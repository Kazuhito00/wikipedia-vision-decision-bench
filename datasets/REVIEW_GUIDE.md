# v1 問題レビュー手順書（レビュアー向け）

v1 は「legacy の 1962 問を 1 問ずつ見直して磨き上げた版」です。あなた（レビュアー）は、渡された **1 つのバッチ（約 60 問）** を全問見て、問ごとに 1 行の判定を書きます。画像を実際に見て判断することが目的です。**問題ファイル（`datasets/questions/`）は触りません。** 書くのは出力ファイル 1 つだけです。反映は `datasets/tools/apply_review.py` が行います。

## 1. 入力と出力

- **入力**: `work/review/batch_<群>_<NN>.json`（例 `batch_photo_03.json`）。先頭に `batch`、`output_file`（出力先の絶対パス）、`n_questions`、`priority_all_wrong`、`priority_majority_wrong`（優先して慎重に見る ID）、`questions`（問の配列）があります。
- **出力**: `work/review/out/<バッチ名>.jsonl`（入力の `output_file` のとおり）。**問 1 問につき 1 行、バッチの全問に対して 1 行ずつ**。1 行は 1 つの JSON（UTF-8、改行は LF）。他のファイルは書き換えません。

### 入力の 1 問の中身

| 項目 | 意味 |
|---|---|
| `id` / `legacy_id` | v1 の ID / 元の legacy の ID。出力には **`id`（v1 の ID）** を書く |
| `group` | photo（実写 1268）/ biz（業務画像・描画 288）/ rsn（推論・描画 319）/ txt（文章のみ 87） |
| `kind` | `choice`（選択）/ `noul`（はい・いいえ）/ `score`（段階評価） |
| `en` / `ja` | 各言語の設問。`instr`。choice: `options_as_shown`（**モデルが実際に見た順**の選択肢）、`expected_index`（正解の位置）、`correct`、`wrong`。noul: `truth`（正解。true = はい）。score: `levels`、`expected_index`。txt: `state`（記事本文）と `article_title` |
| `difficulty`, `tags`, `source`, `image_type`, `skill`, `answer_format` | 現在の付け方（`image_type`・`skill` は旧タグからの粗い自動付与。既定の `photo-other` と `figure` は特に怪しい） |
| `images` | **画像ファイルの絶対パス**（モデルが実際に受け取った 224px 画像）。**Read ツールで開いて必ず見る。** txt は空。`two_images: true` の問は 2 枚 |
| `old_results` | 既存 10 モデルの en/ja の正誤（`per_model`）、`answered`、`wrong`、`priority`（`all_wrong` / `majority_wrong` / `normal` / `no_results`）。txt は測定なし（`no_results`） |

画像は 224px に縮小されています。**モデルが見たのと同じ解像度で判断してください。** 224px では判読できない文字・細部を前提にした問は、それ自体が問題点です（`issues` に書く）。

## 2. 判定（verdict）

| verdict | いつ | 必須の項目 |
|---|---|---|
| `ok` | 問題なし。そのまま使える | `issues` は空でよい |
| `fix` | 直せば使える（文言・誤答・正解・難度・分類の修正） | `fix`（変える項目だけ）と `reason` |
| `drop` | 直しても使えない（画像だけでは決まらない、画像が不適切、個人を特定する顔写真、正解が確認不能で代案がない、など） | `reason` |
| `rewrite_1image` | **2 枚画像の問だけ**。1 枚で答えられる形に作り直す必要がある（新しい画像が要る）。作り直せないなら `drop` | `reason`（どの形に作り直すか。例: 「左の 1 枚だけで答えられる比較問に」） |

2 枚画像の問（`two_images: true`、13 問）は `ok` / `fix` にできません（1 問 1 枚の規則）。

## 3. チェック項目

**(a) 画像を見て正解が一意に決まるか。** 画像だけでは決まらない（記事の知識が要る、見えない部分に依存）、正解が複数ある、**正解が誤っている**、を見つける。正解が誤りなら `fix` で正解を直す（`correct_*` または `truth` / `score`）。直せるかどうかは**画像で確認できる範囲だけ**で決める。確認できなければ `drop`。

**(b) 誤答（wrong）の質。** 誤答が正解に近すぎて別解になっていないか（例: 犬の写真で「犬」と「子犬」）。逆に、正解以外が明らかにありえない（写真と無関係）簡単すぎる誤答だけで、実質、当て推量で解ける問になっていないか。紛らわしさは「見れば区別できるが、雑に見ると間違える」程度が適切。

**(c) 選択肢の重複・並べ替えで意味が変わる問。** 選択肢どうしが同じ意味、「上記のすべて」「どちらも」など位置に依存する選択肢、「前の選択肢」など順序に依存する言い方。v1 は選択肢を並べ替えて出すので、順序に依存する問は `fix` か `drop`。

**(d) 英語・日本語の自然さと一致。** 機械翻訳くさい日本語（直訳調、主語の不要な反復、不自然な敬語）、日本語で言い換えるべき固有表現（地名・制度・単位・色名の慣用）。**en と ja で意味が違っていないか**（数・否定・条件・正解の対応）。日本語の問は、日本語として自然な言い方に直す。直した日本語が英語と意味がずれないようにする。

**(e) 難度の妥当性。** easy / medium / hard。見て一目で分かるなら easy、細部・読み取り・複数手順が要るなら hard。`old_results` を参考にするが、モデルの正誤だけで決めない（正解が誤っているだけかもしれない）。

**(f) 分類軸の付け直し。** `image_type`、`skill`、`answer`（形式）。特に既定値の `photo-other`（実写）と `figure`（描画）は、画像を見て細かく付け直す。使える値は次のとおり。
- `image_type`: photo-animal, photo-plant, photo-vehicle, photo-food, photo-structure, photo-person, photo-scene, photo-object, photo-other, art, document, text-in-image, diagram-map, sign, mixed（どの種類の画像かを問う問）, chart, ui, figure（問のために描いた図形・矢印・ダイヤル等）。txt は `none` のまま
- `skill`: recognition, ocr, count, spatial, compare, quantity, rules, negation, contradiction, uncertainty。txt は `text-comprehension` のまま
- `answer`（形式）は選択肢の数から自動で再計算されるので、書いても書かなくてもよい（書いても採用されない）

**(g) 2 枚画像の 13 問。** 1 枚の画像だけで答えられる形に作り直せるか。作り直せるなら `rewrite_1image` と、その形を `reason` に具体的に書く。作り直しても本質が変わってしまう（2 枚の比較が肝）なら `drop`。

**(h) 画像と設問の矛盾、不適切な内容。** 画像と設問が矛盾していないか。**個人を特定できる顔写真**（人物が主題で、名前を当てさせる、または特定の個人が分かる）、不適切・差別的・暴力的な内容は `drop`（`issues` に `privacy` や `inappropriate` と書く）。

**(i) 全モデルが外した問・半数以上が外した問は特に慎重に。** `priority_all_wrong` / `priority_majority_wrong` の問は、**正解が誤っている**、**設問が曖昧**、**画像が小さすぎて判読できない**のどれかである可能性が高い。画像を丁寧に見て、原因を `reason` に書く。原因が「本当に難しいだけ」なら `ok`（`issues` に `hard-but-valid`）。モデルが外したことだけを理由に `drop` や難度変更をしない。

**(j) 不足種類の指摘（バッチ単位ではなく、問ごとの気づき）。** 次のような問が足りない／足せそうだと気づいたら、該当する問の `issues` に書く（例: `could-be-2-options`, `could-have-6-options`, `score-3-levels`, `negation-variant`, `count-variant`, `position-variant`, `none-of-the-above-variant`, `text-only-control`, `ja-specific`）。対象は、選択肢数 2 / 5〜10 の変種、段階評価の段階数（3・7・10 など）、否定形（〜でないもの）、数える、位置関係、「該当なし」が正解の問、画像の問の文章のみの対照（画像なしで答えられてしまう問を見つける）、日本語固有（画像内の日本語など）。**新しい問そのものを作る必要はありません**（指摘だけ）。

## 4. 出力の書式（1 問 1 行）

```json
{"id": "photo-0012", "verdict": "fix", "issues": ["wrong answer too close", "ja unnatural"],
 "fix": {"wrong_en": ["goat", "pig", "rabbit"], "wrong_ja": ["ヤギ", "豚", "ウサギ"], "instr_ja": "主に写っている動物はどれですか？", "difficulty": "easy"},
 "reason": "「子羊」は「羊」と別解になるため誤答から外した。日本語の語順を自然にした。"}
```

- `id`: 入力の `id`（v1 の ID）。**バッチの全問に 1 行ずつ。重複・欠落・ほかのバッチの ID は不可。**
- `verdict`: `ok` / `fix` / `drop` / `rewrite_1image`
- `issues`: 見つけた問題の短い文字列の配列（`ok` でも気づきがあれば書く。なければ `[]`）。
- `fix`: **`verdict` が `fix` のときだけ、変更する項目だけ**を入れる。使えるキー:

| キー | 型 | 意味 |
|---|---|---|
| `instr_en`, `instr_ja` | 文字列 | 設問文 |
| `correct_en`, `correct_ja` | 文字列 | 正解の選択肢（choice のみ） |
| `wrong_en`, `wrong_ja` | 文字列の配列 | 誤答（choice のみ）。全体を置き換える。**en と ja の個数を同じにする。正解と同じものを入れない。重複・空文字は不可。選択肢は合計 2 個以上** |
| `truth` | true / false | はい・いいえの問の正解（noul のみ）。`true` = はい |
| `levels_en`, `levels_ja` | 文字列の配列 | 段階評価の段階の文言（score のみ。en と ja の個数を同じにする） |
| `score` | 整数 | 段階評価の正解の段階（0 始まりの位置。score のみ） |
| `difficulty` | easy / medium / hard | |
| `image_type`, `skill` | 文字列 | 上の一覧の値 |
| `answer` | 文字列 | 形式の軸（`choice:5` など）。書いても自動で再計算されるので省略してよい |

  選択肢を足す・減らすときは `wrong_en` と `wrong_ja` の**両方**を同じ個数で書く。選択肢の並び順は書かない（実行時に決まる）。`ok` / `drop` / `rewrite_1image` に `fix` を付けない。
- `reason`: **`ok` 以外は必須**。何を見て、なぜそう判断したかを 1〜2 文で。

### 書いてはいけないもの

- **数値・固有名詞・事実を、画像で確認できないのに作らない。** 画像から読み取れないことは、「確認不能」と `reason` に書き、`drop`（または `ok` のまま `issues` に `unverifiable`）にする。自分の知識で正解を決めない。224px で読めない文字は「確認不能」。
- 問題ファイルや `batch_*.json` を書き換えない。他の出力ファイルを作らない。
- 画像を見ずに判定しない。`images` の絶対パスを Read で開く。

## 5. 進め方（推奨）

1. このガイドと、入力バッチの先頭（`priority_*`）を読む。
2. 問を順に処理する。画像のある問は、**先に画像を見て自分で答えを決め**、そのあとで `correct` / `truth` と比べる（先に答えを見ると引きずられる）。
3. `priority_all_wrong` の問を先に見ると効率がよい（ただし出力は全問、元の順でなくてもよい）。
4. 全問の判定を書いたら、出力ファイルの行数が `n_questions` と一致することを確かめる。
5. 確認: `python datasets/tools/apply_review.py`（dry run。何も書き換えない）が通れば書式は正しい。

## 6. 反映（人間・ツール側）

`python datasets/tools/apply_review.py`（dry run）で検証と差分の要約を見て、問題なければ `--apply` を付けて実行する。`review.state` は ok → `reviewed`、fix → `changed`、drop → `dropped`、`rewrite_1image` → `reviewed`（id 対応表の `status` は `pending` のまま、`change_note` に作り直しの内容）。履歴 `review.history` に `{date, what, why}` が入る。外した問（`dropped`）は問題ファイルに残るので、ローダー・ランナー側で `review.state == "dropped"` を除外すること。同じ出力を 2 回反映しても結果は変わらない。

## 追記（試行レビューの指摘から、2026-10-11）

- **重複問**: 画像が同一（バイト一致）で、設問・選択肢も同じなら、後の方を `drop`、issues に `duplicate`（どの問の重複か ID を書く）。
- **ok のまま注記**: 設問が少し曖昧だが答えは一意に決まる場合は `ok` とし、issues に書くだけでよい。答えが 2 通りに読める、または画像だけで決まらないなら `fix`（設問の明確化）。
- **画像の欠陥**（行き先のない矢印、判読不能など）は issues に `image_defect:` で始めて書く。答えに影響するなら `drop` または `fix`。
- 画像パスが開けないときは、`wiki_qa\work\px224` の同名ファイルを探す（バッチの画像パスは存在確認済み）。
- 既存モデルの結果は正誤だけで、どの選択肢を選んだかは分からない。全モデルが外した問は、自分で解いて正解の妥当性を確かめること。

## 追記2（photo_01 の試行から、2026-10-11）

- **(h) の運用**: 画像は CC0/パブリックドメインの Commons 写真で、設問が人物の同定を求めない限り、人物が写っているだけで `drop` にしない。人物の写真は issues に `privacy-check` と書いて `ok`/`fix` とし、drop を決めるのは人間（ユーザー）。例外: 設問が人物の同定・識別を要求するときだけ `drop`/`fix`。
- **画像の種類を問う問**: 誤答に「写真」を入れない（天体画像・衛星画像も写真であり別解になる）。衛星画像・地図・イラスト・図・スクリーンショット等で代える。
- **日本語の選択肢**: 画像内の印刷された文字を読む問は、ja の選択肢も印刷された原語のまま（邦題・訳語にしない）。
- **誤答が簡単すぎる**問（正解と明らかに別カテゴリ）は、紛らわしい誤答（正解に近い別物）に替える fix を提案する。ただし新しい誤答が**画像で別解にならない**ことを確認する。
- `image_type` に合う値がないとき（天体画像など）は、近い値を選び issues に `needs_new_image_type: <提案>` と書く。

## 新問（`new_<tag>.jsonl`）のレビュー

v1 に後から足した問（`origin: "new"`。作り方と ID の予約範囲は `NOTES.md` §10）は、同じ手順・同じ出力書式でレビューする。違いは次のとおり。

- **入力**: `work/review/new_<tag>_<NN>.json`（約 60 問、ID 順。`python datasets/tools/export_review_batches.py --new <tag>` が作る）。**出力**: `work/review/out/new_<tag>_<NN>.jsonl`（バッチ名と同じ。1 問 1 行、全問）。出力の書式・verdict・fix のキーは上と同じ。`rewrite_1image` は使わない（新問は 1 問 1 枚）。
- 1 問の中身の違い: `new: true`、`legacy_id` は `null`、`derived_from`（派生元の v1 ID。あれば**その問も見比べる**）、`relation`、`lang`（`ja` の問は `ja` 側だけ）、`images`（画像問は 224px のパス。文章のみの対照は空）。choice の `options_as_shown` は**実行時にモデルが見る順**（balanced）で、`option_labels`（A, B, C …。10 択以上でも位置を指せる）が付く。旧モデルの結果（`old_results`）は無い。txt の対照は、自作の `state`（画像が無いと書いた短い文）が入っている。
- 画像は先に自分で見て答えを決めてから `correct` / `truth` / `score` と比べる（上の「進め方」と同じ）。

### 新問のチェック項目（上の (a)〜(j) に加えて）

1. **作成意図の一致**: tag の目的（`newq.PURPOSE`、`manifests/gap_analysis_v1.md` の該当行）どおりの問か。例: 「2 択」の問が本当に 2 択か、「否定」の問が否定を問うているか（二重否定になっていないか）、「位置関係」が左右・上下を問うているか、「段階評価」が 3/7/10 段階か、「該当なし」が正解の問が本当に「どれも当てはまらない」か。意図と違うなら `fix`（または `drop`）。
2. **正解の一意性**: 画像（対照は state）だけで正解が 1 つに決まるか。派生問は、親から変えた点（選択肢の数・反転・否定）に合わせて**正解も正しく変わっているか**（反転した画像で左右が入れ替わっているか、否定にしたら正解が反転しているか）。
3. **画像で確認できる**: 224px で判読できるか。画像と無関係な知識に頼っていないか。`mirror`（反転）の変種は、文字が鏡文字になっていないか。
4. **選択肢数ごとの紛らわしさ**:
   - 2 択: 当て推量で 50%。誤答が正解と別解にならないか、はい/いいえの偏りがないか。
   - 3〜5 択: 誤答が「見れば区別できるが雑に見ると間違える」程度か。
   - 6〜10 択: 全選択肢が同じ種類で互いに区別でき、正解以外のどれかが別解になっていないか（選択肢が増えるほど別解が混じりやすい）。画像で全選択肢を消去できるか。
   - 12〜16 択（QEV の上限試験）: 全選択肢が重複・言い換えでなく、1 つだけ正しいか。
   - 段階評価: 各段階に数値の範囲や基準があり、境界が曖昧でないか。正解の段階が 1 つに決まるか。段階を並べ替えても意味が変わらないか（段階は並べ替えない。順序どおりか）。
5. **「該当なし」類**: 正準の表記か（`NOTES.md` §10.5）。en と ja で同じ位置に同じ意味があるか。「該当なし」が安易に選べる問になっていないか（同じ画像の「該当あり」の対と対にしてあるか）。順序に依存する選択肢（「上記のすべて」）が無いか。
6. **日本語固有の自然さ**（`lang: ja` の問）: 日本語として自然か（翻訳調でない）。日本語の知識（曜日・干支・単位・敬語・看板）が正しいか。画像内の日本語が 224px で読めるか。英語版が無いことで一意性が崩れていないか。
7. **文章のみの対照**: 画像が無いと答えが決まらない（画像が無くても答えが分かってしまう問は、元の問が画像に頼っていないことを示すので `issues` に書く）。state に Wikipedia の本文をコピーしていないか。`derived_from` の元の問と設問が一致しているか。
8. **新設の分類の妥当性**: `image_type`・`skill`・`difficulty` が画像と問に合っているか（既定の `photo-other` / `figure` に逃げていないか）。`taxonomy.py` に無い値が必要なら、近い値を選び `issues` に `needs_new_image_type: <提案>` と書く（値の追加は調整役が決める）。`derived_from` と `source` が整合しているか。重複は `drop`（`issues` に `duplicate`）。**変種は重複ではない**: 親と同じ画像でも、選択肢の数や種類（4 択 → 6 択、選択 → はい/いいえ）、設問文（否定）、画像（反転）、正解が変わっていれば別の問。同じ画像・同じ設問・同じ正解・同じ選択肢の数で、誤答の組だけ違うものは重複（`validate_new.py` も後ろの ID をエラーにする）。
9. **本文・個人情報**: 記事の本文のコピー、人物の同定を求める問は `drop`。

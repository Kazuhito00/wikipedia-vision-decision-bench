Wikipedia 画像セット — 型付き判定モデルの比較

Wikipedia / Wikimedia Commons の CC0・パブリックドメインの写真・図と、スクリプトで描いた合成の実務画像に、同じ質問を英語と日本語で聞いたときの正解率です。画像のみ・224px に縮小・選択肢は元の順で 1 回だけ聞いています。

データセット言語

ONNX の作り方（自前の export が要るか）

どのモデルも実行時は onnxruntime と numpy などで動き、torch は要りません。torch が要るのは export と検証用の参照実装だけです。

モデル自前の exportONNX の入手元
OneJev 0.8B不要公開 ONNX を prepare_model.py で取得（HTTPS のみ）
OneJev 4B重みの差し替えのみ公開されていないため、Qwen3.5-4B の公開 ONNX のグラフに OneJev-4B の重みを差し替えて作成（build_onnx_4b.py）。torch での export はしていません。差し替えルールは元の Qwen3.5-4B で公開 ONNX を再現できることを先に確認し、PyTorch fp32 との比較は 17/17 で判定一致（最大ロジット差 0.006）
OpenJev 0.8B / 4B不要公開 ONNX を取得（prepare_model.py）
JEVision 0.8B重みの差し替えのみ公開されていないため、Qwen3.5-0.8B の公開 ONNX のグラフに、Base と LoRA を統合した重みを差し替えて作成（pointer head 用に隠れ状態を出力）。torch での export はしていません
QEV 2B必要Strands と同じ方式（torch で固定長の torso を export、head は numpy の npz）。固定長 L=256 / 384 / 512 / 1024 / 1280 / 2048 の 6 本が 1 組の重みを共有
Intern-Decision 0.8B必要checkpoint を取得して export_onnx.py で書き出し（torch / transformers / onnx が要る）
Strands Decider 2B必要merge_lora.py で LoRA を統合し、export_onnx.py と export_vision.py で書き出し
clef-flash 9B不要（グラフ流用）ollaya のグラフ（重みなし）と Cloudflare 公式の safetensors をバイトオフセットで参照

モデル精度構成（ファイルと大きさ）合計

OpenJev 0.8Bfp16同上（同じ Qwen3.5-0.8B の 3 グラフ）約 2.1 GB
JEVision 0.8Bfp16decoder（text 用・visual 用）各 1.0 GB / embed 0.5 GB / vision 0.2 GB約 2.7 GB
QEV 2Bfp32torso（L=256〜2048 の 6 本が重みを共有）/ vision_encoder / head（npz）全バケットで約 9.3 GB
Intern-Decision 0.8Bfp32単一グラフ model_L512（読み出し gather 内蔵、系列長 512 固定）3.1 GB / vision 0.4 GB約 3.5 GB
Strands Decider 2Bfp32torso 7.3 GB の重みを、長さ別の L=128 / 384 / 512 / 1024 / 1280 の各グラフが共有 / vision 1.3 GB / head（npz）5 MB1 本使うと約 8.6 GB
OneJev 4Bfp16decoder 8.0 GB（外部データ 5 分割）/ embed 1.2 GB / vision 0.6 GB（3 グラフ）約 9.9 GB
OpenJev 4Bq4f16decoder 2.3 GB / embed 0.35 GB / vision 0.19 GB（3 グラフ）約 2.9 GB
clef-flash 9Bbf16 の重みを fp32 グラフが参照グラフ 12 MB（重みなし）/ 公式 safetensors 4 分割 約 18 GB / joint_head 0.23 GB / vision 1.7 GB約 20 GB
0.8B の 2 本は q4f16 版（合計 約 0.6 GB）も置いてあるが、評価は fp16。OneJev 4B（fp16）と OpenJev 4B（q4f16）はサイズが約 3.4 倍違うので、比較には精度の違いも含まれる。clef-flash は重みを bf16 のまま置き実行時に fp32 へ展開するため、9B で RAM を約 14〜16 GB 使う。

GitHub Release に置くときの分割（予定）

GitHub Release のアセットは1 ファイル 2 GiB（2,147,483,648 バイト）未満、1 リリース最大 1000 ファイル（合計サイズの上限なし）です。取得は、これまでと同じく素の HTTPS で行い、git-lfs は使いません。

対象いまのサイズ（MiB）対応
OneJev 4B の decoder5 分割（最大 1999）上限（2048）に近く余裕が小さい。1.9 GiB 程度の分割に作り直すと安心
OpenJev 4B の decoder1972 + 351上限内（余裕は小さい）
Intern-Decision の model_L5121900 + 971上限内
0.8B 系、embed、vision最大 1436そのまま置ける
Strands の torso7179（重みは長さ別グラフで共有）分割が必要
clef-flash の safetensors3753〜4757（4 本）分割が必要
分け方は 2 通り。(1) ONNX の外部データを再分割する（shard_external_data.py を流用。ダウンロード後そのまま使える。ただし 1 つで 2 GB を超えるテンソルは割れない）。(2) バイト列で機械的に分割し（split -b 1900m など）、取得側で連結する（結合後の sha256 を照合できる）。
方針：公開する 4B 系と Intern は (1)、Strands は (1) が通るか確認してから決め、clef-flash は公式 safetensors を sha256 照合付きで取る作りなので (2)（sha256 の一覧を Release に添える）。取得側の prepare_model.py は Release のアセットを HTTPS で取り、sha256 を照合する形にする。

見どころ

    正解率

    種類・難度・内容別の正解率

    緑が濃いほど高く、赤みがかるほど低い正解率です。問数が少ない行（8 問未満）は省いています。

    言語の比較（同じ設問だけ）

    同じ画像に同じ内容の質問を英語と日本語で聞いた設問だけを取り出して比べます。符号検定は、片方の言語でだけ正解になった問の数で行います。

    速さ・コスト

    速さは、1 モデルずつ測った 1 問あたりの中央値（機械の基準測定が静かな時の約 3 倍以内のものを「静かな状態」とします）（CPU 8 スレッド・画像の前処理を含む）で比べます。散布図は、静かな状態の時間があるモデルだけを載せます。基準測定が静かな時の約 3 倍を超えて機械が混んでいた・遅かった測定の時間は、下の表に「※ 参考値」として示します。

    データセットごとの 1 問あたりの推論時間（中央値）

    モデル間の差は誤差ではないか

    同じ設問で「A だけ正解」「B だけ正解」になった数を数え、符号検定（両側）の p 値を出します。小さいほど「偶然ではない差」です。

    同じモデルの大きさ違い・微調整の有無（参考）

    別のモデル同士の比較（上の表）とは問いが違うので分けます。OpenJev 0.8B と 4B は同じ方式の大きさ違い、OpenJev 0.8B は素の Qwen3.5-0.8B にプロンプトで判定させたもの、OneJev・Intern-Decision はそれを微調整したものです。分かるのは「大きくすると」「微調整すると正解が増えるか」であって、モデルの優劣ではありません。

    難問と、全員が解けた問

    何モデルが正解したかの分布です。「全員不正解」には設問・正解の誤りが混ざっている可能性があるので、一覧で確認できます。

    設問一覧

    問ごとに、質問・選択肢・正解・各モデルの答えを見られます（緑＝正解、赤＝不正解）。画像をクリックすると、モデルに入力した大きさで拡大表示します。
    時間は、静かな状態で測ったものを通常の表示、機械が混んでいた・遅かった測定は「※」付きの薄い斜体の参考値で示します（補完・拡充・合成・Strands・clef-flash の最初の測定など）。OpenAI の時間はネットワーク往復で、機械の状態に左右されません。
